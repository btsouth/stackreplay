# Catalog intelligence evidence contract (M4H-B)

## Trust boundary

`@stackreplay/catalog/intelligence` describes **candidate research**, not accepted catalog data. The accepted catalog remains the four YAML directories under `packages/catalog/data`, loaded by `loadCatalogFromDirectory` and embedded by the bundled catalog build. The catalog root export, loader, public read model, changelog, target selection, and Replay engine do not import candidate intelligence. A candidate's `review.status: "accepted"` means only that a human decision was recorded on that artifact. It does not create a plan version, alter a price or limit, make a model available, add an alias, or change a Replay result. A future workflow must make and review an explicit catalog edit before any fact becomes accepted.

Candidate JSON belongs in a separate internal artifact location supplied by a caller, never in accepted catalog data directories. This milestone provides schemas, pure validation, a deterministic ID, and canonical serialization; it does not store candidates or snapshots. No candidate or registry entries with real provider facts have been added.

## Source registry and authority

A version 1 registry entry has a stable ID and HTTPS URL, optional provider association, source kind, authority, allowed claim kinds and evidence classes, lifecycle status, and optional retrieval mode, label, and note. Provider pricing, docs, changelog, and pages are provider-owned; archive, third-party, community, and measurement are distinct roles. Registry validation rejects duplicate IDs, duplicate claim eligibility, invalid URLs, and inconsistent roles. Only provider-owned sources may offer `published` evidence. A candidate must match its registered URL, permitted claim kind and evidence class. A source's eligibility is a limit on what it may propose, never acceptance authority.

`published` means a provider-owned source explicitly states a claim. `observed` means a measurement or historical observation indicates behavior or text. `unsupported` means the evidence does not establish the claim. Extraction method (`manual`, parser, diff, LLM assisted, measurement) records how a draft was made and grants no authority. One published-truth claim policy covers prices (including overage), numeric and qualitative limits, availability, aliases, and effective dates. Observed evidence on any of those claims receives `observed_not_published`; unsupported evidence receives `unsupported_not_published`. Both remain serializable review artifacts. An archival copy can support what text was seen, but retrieval time alone cannot prove when the rule took effect.

Source health has its own explicitly versioned (`version: 1`) shape for a later retrieval system: attempt/success times, status, redirect, type, fingerprint, failure, and unknown/healthy/failed/stale state. Unsupported versions fail parsing. It is not stored in the registry or catalog and never clears accepted facts. Snapshot references contain an internal ID and SHA-256 fingerprint, not page text. Evidence carries only a short excerpt (300 characters maximum) or URL reference. Source and evidence URLs require HTTPS, a hostname, no credentials, and no raw whitespace or control characters. Ports, query strings, fragments, and normal domain encoding are allowed; validation makes no network request.

## Candidate contract

Version 1 candidates carry an exact ID, registered source reference, observation timestamp, optional source publication date and snapshot pair, a typed claim, evidence class and short evidence, extraction method, optional prior accepted catalog reference, optional proposed effective date with its evidence, and review metadata. Unsupported contract versions fail schema parsing. Validation returns deterministic findings with severity, code, path, and message; severity is not approval state. It performs no fetch, write, clock read, mutation, identity matching by similarity, or catalog normalization.

Claim kinds map to current catalog concepts: subscription base price; API list or target billing rate; overage price; numeric or qualitative plan limit; model availability; exact alias; effective date; and a precisely described unclassified source change. Subjects name plan, plan version, model, pricing record, limit, provider, or exact source string as applicable. A raw model name is retained for review and does not become a canonical model ID, alias, route, or translation. Proposed values are typed but partial. Missing amount, currency, unit, billing interval, pricing basis, token category, model scope, reset window, exceed behavior, normalized value, or effective date remain absent, including for `proposed: {}`. A candidate calendar window has its own schema; absent timezone remains absent instead of inheriting the accepted catalog's UTC default. Validation names gaps without inserting a default or zero. Against a supplied accepted catalog, it also checks plan/version, constraint/plan/version, pricing/model, provider/plan, alias/model, and recorded model/provider relationships without mutating any record.

`observedAt` is when the caller observed the source. `sourcePublishedOn` is a source's publication date when known. `proposedEffectiveDate` is separate and requires explicit provider-owned **published** evidence; provider ownership by itself and `observed` or `unsupported` evidence are insufficient. A missing effective date receives `effective_date_unestablished`; a date inferred solely from retrieval or archive time receives `effective_date_unsupported`. Effective dates are never copied from observation time.

The ID identifies a **candidate artifact**. It is SHA-256 of canonical JSON for contract version, source ID and URL, source publication date, snapshot references, exact typed claim and proposed value, previous accepted reference, proposed effective date and its evidence, evidence class, short evidence excerpt/reference, and extraction method. Decimal amounts are canonicalized for identity (`20` and `20.00` match), while the artifact preserves the source-facing value. Review status, reviewer, decision time, accepted catalog version attached to review, and repeated observation time are excluded as mutable review/provenance context. Existing IDs can be supplied to validation to flag exact duplicates. `serializeCandidate` sorts keys recursively for stable JSON diffs.

## Review and later phases

`pending` and `needs_review` need no decision metadata. `accepted`, `rejected`, and `superseded` require reviewer and decision time; an accepted catalog version reference may be attached later by an external reviewed process. None of these statuses invokes a catalog writer.

**Implemented:** registry, candidate and health reference schemas; deterministic ID and serialization; pure validator and specific findings; synthetic tests including Replay isolation.

**Planned:** M4H-C historical LimitWatch evidence review as candidate artifacts only; M4H-D fetch/snapshot, source health monitoring, candidate generation, watchers and PR automation; M4H-E accepted target change index and Replay freshness. A future watcher can supply a retrieval result and snapshot reference to a candidate without this contract assuming how retrieval happens. Future affected-target tracing can use exact subject IDs and prior accepted record references. No LimitWatch code or historical facts were migrated.
